# V4.2 集群容量、可靠性与性能测试报告（2026-08-11）

## 摘要

本报告覆盖当前提交 `19f7b2e` 在真实 `/data` 磁盘上的已完成测试：
Multi-Reactor 正确性、双节点性能矩阵，以及 2/3/4 DataNode 的上传即时准入容量。

结论：在副本数为 2、每个 DataNode 默认 `maxActiveUploads=2` 时，实测集群可稳定
同时接纳 2、3、4 个文件上传，分别对应 2、3、4 个节点。超过该容量的请求在
Gateway 路由阶段稳定得到 `503 + Retry-After`，没有出现 hash 校验失败或异常 `400`。

## 环境与方法

- 构建：`RelWithDebInfo`，GCC 11.4，CMake 3.22
- 主机：8 vCPU，约 2.8 GiB 内存，2 GiB Swap
- 磁盘：`/data` ext4，约 491 GiB
- 部署：同机 loopback Gateway 1 个，DataNode 2/3/4 个；每对象链式双副本
- 对象：16 MiB，4 个 4 MiB Chunk；每档 3 轮
- DataNode：`MINIKV_V4_IO_THREADS=2`（双节点性能对比另含 0）
- 默认资源治理：每节点上传槽 2、下载槽 8；每客户端上传槽 2、下载槽 4
- 成功的端到端样本均下载并做完整 SHA-256 校验；upload-only 容量样本在 Gateway
  commit 成功后计为成功。

所有集群、日志和 CSV 都在：

```text
/data/minikv-v2/v4-perf-20260811-fMiSq5/
```

## 双节点端到端性能

双节点、双副本、16 MiB、每档 3 轮。P50 为成功文件的完成时间；并发 4/8 的成功数
受默认上传准入限制。

| I/O loops | 并发 | 成功/请求 | 上传 P50 | 下载 P50 |
|---:|---:|---:|---:|---:|
| 0 | 1 | 3/3 | 314.207 ms / 50.92 MiB/s | 146.587 ms / 109.15 MiB/s |
| 0 | 2 | 6/6 | 291.691 ms / 54.85 MiB/s | 176.796 ms / 90.50 MiB/s |
| 0 | 4 | 6/12 | 240.010 ms / 66.66 MiB/s | 169.746 ms / 94.26 MiB/s |
| 0 | 8 | 6/24 | 245.456 ms / 65.18 MiB/s | 162.045 ms / 98.74 MiB/s |
| 2 | 1 | 3/3 | 344.622 ms / 46.43 MiB/s | 150.872 ms / 106.05 MiB/s |
| 2 | 2 | 6/6 | 277.360 ms / 57.69 MiB/s | 168.296 ms / 95.07 MiB/s |
| 2 | 4 | 6/12 | 240.000 ms / 66.67 MiB/s | 160.484 ms / 99.70 MiB/s |
| 2 | 8 | 6/24 | 277.217 ms / 57.72 MiB/s | 187.117 ms / 85.51 MiB/s |

`io_threads=2` 在并发 2 上传上有约 5% 的 P50 改善，但单流和受限并发下没有稳定
收益；不能据此宣称 Multi-Reactor 使吞吐倍增。

## 多节点上传容量

上传专用模式：成功条件为文件的所有 Chunk 完成双副本并被 Gateway commit。

| 节点数 | 双副本 | 每节点上传槽 | 并发 | 成功/请求 | 上传 P50 | 结论 |
|---:|---:|---:|---:|---:|---:|---|
| 2 | 2 | 2 | 2 | 6/6 | 291.691 ms（端到端矩阵） | 稳定容量 2 |
| 2 | 2 | 2 | 4 | 6/12 | 240.010 ms（成功流） | 每轮 2 个 503 |
| 3 | 2 | 2 | 3 | 9/9 | 236.026 ms / 67.79 MiB/s | 稳定容量 3 |
| 3 | 2 | 2 | 4 | 9/12 | 253.854 ms / 63.03 MiB/s | 每轮 1 个 503 |
| 4 | 2 | 2 | 4 | 12/12 | 273.041 ms / 58.60 MiB/s | 稳定容量 4 |
| 4 | 2 | 2 | 5 | 12/15 | 280.553 ms / 57.03 MiB/s | 每轮 1 个 503 |

实测与下式一致：

```text
集群即时文件上传容量 = 节点数 × 每节点上传槽 ÷ 副本数
```

这里为 `N × 2 ÷ 2 = N`。这证明当前 `2` 是每节点保守且可验证的默认值；它不是
集群只能处理两个文件，而是双节点集群在双副本条件下只能同时处理两个文件。

## 已知不足与未覆盖项

以下内容**未完成实测**，不能从本报告推出结论：

- download-only 的并发容量；`maxActiveDownloads=8` 目前仅是配置值，不是实测上限；
- 真正上传/下载 mixed 负载下的成功率、吞吐和相互影响；
- Chunk P50/P95/P99、控制面 QPS、EventLoop lag、CPU/RSS、outputBuffer 峰值；
- 磁盘 BlockPool 余量、队列峰值与 pause 聚合；
- 火焰图与跨机/跨机架网络表现；
- 503 后按 `Retry-After` 自动重试的最终完成率。

现有 benchmark 已增加模式 CLI 合同，并已实现 upload-only；download-only 与 mixed
执行路径尚未完成，因此本报告不将下载槽 8×节点数的理论值冒充为测试结果。

## 优化前的判断

当前证据表明扩充 DataNode 能按副本约束线性提高上传即时容量。下一阶段应先补齐
download-only、mixed 和队列/延迟观测，再决定优先做副本长连接池、并行 Chunk window、
SharedBodyBlock/writev，还是读写公平调度。
