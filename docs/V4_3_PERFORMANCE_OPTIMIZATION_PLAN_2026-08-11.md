# V4.3 性能优化与验证计划（2026-08-11）

## 目标与原则

本阶段在 V4.2 Multi-Reactor 基础上继续优化 MiniKVCine 的数据面性能与稳定性，
不重写现有 Gateway、DataNode 或网络框架。重点不是单独追求更高的 epoll 线程数，
而是先确认并消除真实瓶颈：副本短连接、Chunk 串行、数据拷贝、磁盘队列以及读写抢占。

所有性能结论必须来自相同硬件、相同构建类型、相同对象大小和可保存的原始 CSV/日志。
优化必须同时满足正确性与资源上限：不能以取消写入准入、无限制缓存或放大内存池换取吞吐。

## 当前基线

- 提交基线：`19f7b2e feat: add V4 multi-reactor datanode`。
- 环境：8 vCPU、约 2.8 GiB 内存、`/data` ext4；Gateway 和 2--4 个 DataNode 均为同机 loopback 进程。
- 对象：16 MiB，4 个 4 MiB Chunk，链式双副本。
- 双节点、双副本、每节点 2 个上传槽时，稳定即时上传容量为 2 个文件；3/4 节点分别为 3/4 个文件。
- `MINIKV_V4_IO_THREADS=2` 只在并发 2 上传中带来约 5% 的 P50 改善，单流及受准入限制的高并发没有稳定收益。
- 当前已实现：上传专用压测模式；端到端上传后下载校验；Multi-Reactor 生命周期测试。
- 当前未实现或未完整测量：download-only、真正 mixed、Chunk 延迟、控制面 QPS、EventLoop lag、输出队列和磁盘队列聚合指标。

基线原始结果见 [V4.2 集群容量、可靠性与性能测试报告](V4_2_CLUSTER_CAPACITY_TEST_REPORT_2026-08-11.md)。

## 优化顺序

```text
可观测性与负载模型
        ↓
副本连接复用
        ↓
受治理的 Chunk 并行窗口
        ↓
减少副本数据拷贝
        ↓
读写/后台任务公平调度
        ↓
基于指标决定是否继续调整 I/O EventLoop 数
```

后续阶段以前一阶段的测试结果作为是否继续的依据；不预设“更多 epoll 线程必然更快”。

## 阶段 0：固定基线与补齐观测

### 实现

1. 完成 benchmark 的 `download-only` 与真实 `mixed` 模式。
   - `download-only` 先准备并校验固定对象，再只计下载过程；不把上传耗时混入下载结果。
   - `mixed` 在同一集群内同时运行独立上传和下载工作者，分别记录成功、拒绝、错误和端到端时间。
2. 为每个 Chunk 记录开始、上传完成、commit 完成的时间；聚合 P50/P95/P99，不以 `sessionId`、文件 hash 等高基数字段作为指标标签。
3. 增加控制面指标：建会话、routes、commit、manifest 的请求数、成功数、错误码与耗时。
4. 增加资源指标：EventLoop lag、`TcpConnection` 输出缓冲峰值、pause/resume 次数与持续时间、磁盘任务队列峰值、BlockPool 可用块最低值。
5. benchmark 采集 CPU、RSS 和磁盘统计；火焰图作为单独可选采样，不进入每轮基本回归。

### 测试与验收

- 为模式解析、下载夹具、混合调度、百分位聚合和指标标签添加单元测试。
- 2 个节点下执行 upload-only、download-only、50/50 mixed，文件并发 `1/2/4/8`；每档至少 3 轮。
- 2/3/4 节点下执行上传即时容量矩阵，保留 `503 + Retry-After` 的拒绝原因。
- 验收标准：成功下载必须全量 SHA-256 校验；受限时只能出现明确可重试的 503，不能出现无解释 400、悬挂连接或内存无限增长。

### 输出

- 原始 CSV、进程日志、环境快照和一份 V4.3 阶段 0 报告。
- 基于 EventLoop lag、CPU、磁盘队列和副本建立频率，给出瓶颈排序；之后才决定优化收益目标。

## 阶段 1：DataNode 副本长连接池

### 问题

当前每个 Chunk 的副本转发都会新建 HTTP/TCP 短连接，并要求关闭连接。对于 4 MiB Chunk，
连接建立、请求解析、对象分配和 TCP 状态管理会重复出现；多 EventLoop 不会消除这些成本。

### 最小实现

1. 以副本目标 `nodeId + endpoint` 为键维护 DataNode 内部连接池。
2. 每条连接同一时刻只处理一个副本请求，空闲连接可复用；池大小受目标节点、全局上传槽与内存预算限制。
3. 明确连接状态：连接中、空闲、写入中、失败、关闭中；连接不可用时请求回退为新建连接。
4. 处理连接超时、对端关闭、半开连接、写入失败与退避重连；失败连接不得重新借出。
5. 关闭 DataNode 时先停止接收新任务，再取消/归还池中请求并在所属 EventLoop 销毁连接。

### 测试与验收

- 单元/集成测试：复用、并发借用上限、对端关闭、连接超时、重连、DataNode 关闭时的生命周期。
- 保持副本 hash 和 commit 语义不变；连接复用失败必须降级为安全失败或一次受控重建。
- 以阶段 0 的 upload-only 与 mixed 基准比较。重点观察副本建连次数、Chunk P95/P99、CPU 和吞吐；不只比较单一 P50。

## 阶段 2：受全局治理的 Chunk 并行窗口

### 问题

当前单个文件的 Chunk 传输串行，Multi-Reactor 缺少可并行调度的实际工作。直接让所有 Chunk 并发会放大内存占用、磁盘队列和副本连接数。

### 最小实现

1. 客户端 benchmark 与协议调用支持每文件固定窗口，例如初始 `window=2`；同一文件最多两个未完成 Chunk。
2. Chunk 任务进入全局调度器前申请预算：上传写槽、BlockPool 块、磁盘队列容量和副本连接配额。
3. 保留每个 Chunk 的独立 hash/commit 语义；文件级 commit 仅在所有 Chunk 成功后执行。
4. 出错时停止该文件后续 Chunk，释放已经预留的资源；已完成 Chunk 可以安全用于断点续传。
5. 初始仅支持固定窗口 1 与 2；自适应窗口必须在有队列和延迟指标后再评估。

### 测试与验收

- 覆盖乱序完成、一个 Chunk 失败、取消、重复提交、资源预算耗尽和关闭过程。
- 比较 `window=1` 与 `window=2`：单文件、并发文件 2、混合负载各至少 3 轮。
- 验收标准：P99、RSS、BlockPool 低水位和磁盘队列不得超过预先定义的安全阈值；若吞吐无明显收益或尾延迟恶化，则保留窗口 1。

## 阶段 3：副本路径的拷贝与发送优化

### 问题

本地落盘与副本转发可能重复持有/复制同一 Chunk 数据，`send()` 临时缓冲也会增加 CPU 与内存带宽压力。

### 最小实现

1. 评估并引入只读引用计数数据块（例如 `SharedBodyBlock`），使本地写入和副本发送共享 Chunk 内存。
2. 使用 `writev` 或等效的分散写，减少 HTTP 头和 Body 拼接产生的临时复制。
3. 为部分写入维护明确的 offset/长度状态；背压时保留块引用，写完或失败后在所属 EventLoop 释放。
4. 不跨线程直接操作连接；跨线程只投递不可变任务或受引用计数保护的数据块。

### 测试与验收

- 覆盖部分写、`EAGAIN`、连接中途关闭、背压恢复、多个副本消费者、引用最后释放。
- 使用 ASan/LSan（条件允许）和长时间混合压测检查 UAF、泄漏和队列失控。
- 验收以 CPU、RSS、复制字节数、outputBuffer 峰值和 Chunk P99 为主；保持 hash 校验和磁盘索引测试全通过。

## 阶段 4：读写与后台任务公平调度

### 问题

下载的 `sendfile` 路径、上传的写盘路径、复制任务和媒体后台任务会竞争 CPU、磁盘和连接资源。仅使用独立准入槽不足以保证尾延迟。

### 最小实现

1. 将前台上传、前台下载、复制、后台媒体/缩略图任务分类，分别设置有界队列与并发预算。
2. 磁盘执行器采用加权或轮转策略，保证上传不会被持续下载饿死，反之亦然。
3. 当队列超过高水位时，对低优先级工作限速或延后，而不是让内存队列无限增长。
4. 保留当前 `503 + Retry-After` 作为准入满载时的外部语义；排队策略若引入，必须有明确最大等待时间。

### 测试与验收

- 运行 25/75、50/50、75/25 上传/下载混合矩阵，并叠加受控媒体任务。
- 观察每一类的成功率、P95/P99、队列等待时间、pause 时间和拒绝率。
- 验收标准：任一前台类别持续有进展；后台任务不能导致前台请求无界延迟或资源泄漏。

## EventLoop 调优的决策条件

在阶段 0--4 完成前，不扩大默认 `MINIKV_V4_IO_THREADS=2`。只有同时满足下列证据，
才执行 1/2/4 I/O Loop 矩阵并考虑调整默认值：

- CPU 尚有余量，但单个 EventLoop lag 或每 Loop 活跃连接数明显偏高；
- 磁盘队列、BlockPool 和副本连接池没有先达到瓶颈；
- mixed 或高连接数负载下，更多 I/O Loop 能降低 P95/P99，且不会使 RSS、上下文切换或错误率恶化。

若只是单流或低并发 loopback 负载变慢，应保留较少的 I/O Loop，避免增加跨线程调度成本。

## 固定测试口径

每个阶段的性能对比至少包含：

- 构建命令：`cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo` 与 `cmake --build build -j2`；
- 集群：2 节点基线，以及 3/4 节点扩展验证；副本数、节点槽数、I/O Loop 数写入报告；
- 负载：16 MiB、并发 `1/2/4/8`、每档至少 3 轮；上传、下载和 mixed 分开报告；
- 指标：总 MiB/s、文件和 Chunk P50/P95/P99、控制面延迟/QPS、503 数量、CPU/RSS、EventLoop lag、磁盘队列、BlockPool、pause 与 outputBuffer；
- 正确性：成功下载的 SHA-256、CTest 结果、失败 HTTP 状态与日志原因；
- 产物：原始 CSV 与日志目录路径，任何无效/中断样本必须显式排除并说明原因。

## 非目标

本轮不做以下工作：多 Gateway、高可用元数据/WAL/GC/Repair、gRPC、跨地域一致性、
用户权限、RAG/AI 业务、无限制自适应并发或为了跑分而绕开资源治理。

这些能力与对象存储产品化有关，但不应与当前数据面性能验证混在同一个优化周期。
